# Upgrade guide: VPS v18 to v19

This release is an additive expand/migrate rollout. Keep the v18 release directory and its database
backup until v19 smoke tests and the stabilisation window pass.

## Before cutover

1. Run the repository lint, formatting, type, unit, contract, migration, load and offline browser
   checks.
2. Create a PostgreSQL custom-format backup and restore it into a disposable database. Verify the
   migration ledger and core user/session tables in the restored copy. Apply the v19 migrations
   twice there, run the candidate read/write probe, then run the v18 image's read/write probe over
   the expanded schema.
3. Preserve the current production environment file. Add strong, server-only
   `MAPOS_RATE_LIMIT_SECRET` and `MAPOS_OPERATIONS_TOKEN` values; set `MAPOS_PUBLIC_ORIGIN` to the exact
   HTTPS origin.
4. Keep synthetic commerce, simulated wallet/inventory and unverified provider integrations disabled
   in production.

## Migration and rollout

The application applies ordered, idempotent expand migrations at startup. New versions 0002–0009
add event, identity, durable layer-import preview/report, commerce and distributed rate-limit
storage without dropping v18 columns or tables. The adopted 0001 checksum includes three historical baseline reconciliation
statements; the pre-cutover restore drill first proves that their old FK/type changes are already
present on v18 and therefore no-op for this upgrade.
Build and health-check the candidate release before changing the `current` symlink, then check the
public health endpoint and a small set of keyless routes through HTTPS.

This single-VPS topology cannot honestly provide a percentage/cookie cohort. The exact staged,
atomic and automatic-rollback sequence—and the still-open traffic-splitting gate—is recorded in
[ADR 0011](../adr/0011-single-node-rollout-and-cohort-gate.md).

## Rollback

Point `current` back to v18 and restart its compose project. The additive v19 tables can remain while
v18 runs; do not contract or drop them in the same release. Restore the pre-deploy backup only if data
integrity—not application code—requires it, because restoring discards post-backup writes.

For a map-layer-only rollback, build with `VITE_MAP_RUNTIME_V2=0`. This bypasses the shared
style-replay lifecycle and returns LayerEngine to direct handles; it does not alter registry
manifests, feature data, caches on disk or UI composition.

## External gates

Real checkout/webhooks, public SDK registry publication, EIP-1271 wallet verification, an actual
Aavegotchi model payload and a confirmed live Base inventory indexer are not enabled by this upgrade.
